# Native routing search: pad-edge contact endpoints

Date: 2026-10-29. Algorithm and synthetic native evidence, not hardware measurements. The accepted board remains **62 unconnected edges**, SHA-256 `d3b1de9ffa2bb61cb4816fc4161a23d73396cba12b0c3b66f15f310e82d561a3`; the 50-edge target remains open.

The control-route search previously sampled pad centres. A new full-width track starting there can inherit a tight neighbouring-land clearance even when a legal copper connection exists at the outer land edge. The search now samples the centre and four local-axis land-boundary points, rotated with the native pad. Each prospective connecting lead still passes the existing native shape/clearance screen, and each completed route must preserve actual filled physical pad groups. This changes no footprint, pad size, net, track width, clearance, current/protection/enable setting or accepted copper.

The [native regression](../../tools/test-native-pad-contact-endpoints.py) uses a 0.70 × 0.20 mm signal land between two 0.20 × 0.70 mm guard lands, with deliberately existing 0.10 mm pad gaps. Another signal land is open, and an unrelated full-width ground track must survive. With **identical source bytes and the same profile**, the centre-only search at f025fb4 leaves **one** native open; the corrected search joins it with **0.20 mm copper / 0.20 mm other-net clearance** and leaves **zero**. The full native DRC retains exactly the same two original pad-clearance findings. Pads, source bytes and ground copper remain fixed; regenerated routing bytes match exactly.
